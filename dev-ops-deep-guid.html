UI Engineering DevOps — Deep Guide

Every tool explained from scratch. How Docker, ECR, CodeBuild, CodePipeline, Kubernetes, Helm, and CloudFront connect to form a production pipeline — with every command, credential, and configuration that makes each step recognise the next.

Docker ECR CodeBuild CodePipeline EKS Helm IAM CloudFront K8s Security

Overview — Why UI Engineers Need DevOps

In the past, a UI engineer wrote code and handed it to an ops team. Today, you own the delivery pipeline. That means knowing how your React app gets from a laptop to a production Kubernetes pod — and being able to debug it when something goes wrong at 2 am.

The pipeline has three phases:

  • Build phase — source code → tested artifact → Docker image
  • Publish phase — Docker image → container registry (ECR)
  • Deploy phase — registry image → running pods on Kubernetes, behind a CDN

Tool Glossary — What Each Thing Actually Is

Before running a single command, understand what you are working with.

🐳
Docker
Packages your app + its entire runtime (Node, nginx, OS libs) into an isolated, portable container. "Works on my machine" becomes "works everywhere."
🗄️
ECR (Elastic Container Registry)
AWS's private Docker image storage. Like Docker Hub but inside your AWS account. CodeBuild pushes images here; EKS nodes pull them.
🔨
CodeBuild
AWS's managed CI server. Reads buildspec.yml, spins up a fresh VM, runs your commands, produces artifacts. No servers to manage.
🔁
CodePipeline
The orchestrator. Watches your git repo and sequences stages: Source → Build → Test → Deploy Staging → Approve → Deploy Prod. It does not build anything itself.
☸️
Kubernetes (K8s)
A platform that manages running containers across a fleet of servers. You declare the desired state ("3 replicas of this image") and K8s continuously makes it so.
🏗️
EKS
AWS Elastic Kubernetes Service. Managed K8s — AWS runs the control plane (API server, etcd) so you only manage worker nodes (EC2 instances that run your pods).
⛵
Helm
Package manager for Kubernetes. Bundles all your K8s YAML files into a chart with variables so you can deploy the same app to staging/prod with different values.
🌐
CloudFront
AWS CDN. Caches your app's static assets at 400+ edge locations worldwide. Users get assets from the nearest server, not your origin. Also handles HTTPS + WAF.
🪣
S3
AWS object storage. Stores files (HTML, JS, images). For purely static apps, S3 + CloudFront replaces a server entirely. Also stores CodePipeline artifacts.
🔑
IAM
AWS Identity and Access Management. Every AWS service talks to another through IAM roles — no passwords, no API keys scattered in code. This is the authentication glue.
🔒
Secrets Manager
Stores sensitive config (DB passwords, API keys). Apps fetch secrets at runtime via IAM — secrets never touch environment files or Docker images.
⚖️
ALB (App Load Balancer)
AWS Layer-7 load balancer. Routes HTTPS traffic to K8s pods. Terminates TLS. Works with the AWS Load Balancer Controller (a K8s operator) to auto-create from Ingress objects.

How Every Tool Connects to the Next

The most confusing part of this stack is not individual tools — it's the authentication and handoff between them. Here is every connection point explained.

💡

The golden rule: In AWS, services authenticate using IAM roles, never hardcoded access keys. A role is a temporary set of permissions that a service assumes. CodeBuild assumes its service role; EKS pods assume IRSA roles. No password is ever stored anywhere in the pipeline.

Frontend Build Optimization

Before code enters any pipeline, your build output must be optimal. A bloated bundle wastes CloudFront bandwidth, slows LCP, and makes K8s image pulls slower. Good optimization compounds across the entire stack.

What Vite Does at Build Time

Vite uses Rollup under the hood for production builds. Rollup performs tree-shaking (removes unused exports), code splitting (splits chunks at dynamic imports), and minification (renames variables, removes whitespace). The output is a set of hashed JS/CSS files in dist/. 

vite.config.tsimport { defineConfig } from 'vite';
import react     from '@vitejs/plugin-react';
import { visualizer } from 'rollup-plugin-visualizer';

export default defineConfig({
  plugins: [
    react(),
    visualizer({ open: true, gzipSize: true }), // opens bundle treemap after build
  ],

  build: {
    target: 'es2020',       // no IE11 polyfills — reduces output size
    minify: 'esbuild',      // esbuild is 20–100× faster than terser
    sourcemap: false,       // never expose source in prod bundle
    chunkSizeWarningLimit: 500,

    rollupOptions: {
      output: {
        // Splits vendor deps into a separate chunk.
        // Browser caches vendor.js across deploys — only re-downloads if deps change.
        manualChunks(id) {
          if (id.includes('node_modules')) {
            if (id.includes('react'))     return 'vendor-react';
            if (id.includes('@radix-ui')) return 'vendor-ui';
            return 'vendor-misc';
          }
        },
        // Content-hash in filename = safe forever caching on CloudFront
        entryFileNames:  'assets/[name]-[hash].js',
        chunkFileNames:  'assets/[name]-[hash].js',
        assetFileNames:  'assets/[name]-[hash][extname]',
      },
    },
  },
});
⟶ How this connects to CloudFront

The [hash] in filenames is a fingerprint of the file content. If main-abc123.js is unchanged, the hash stays abc123. CloudFront can cache it with max-age=31536000, immutable — a full year. When you change the file, Vite produces a new hash (main-def456.js), index.html references the new name, and CloudFront fetches it fresh. No invalidations needed for assets.

Code Splitting — How It Works

React.lazy() wraps a dynamic import(). Rollup sees this import and automatically creates a separate chunk file for that component. The browser only downloads that chunk when the user navigates to that route. 

React — lazy routesimport { lazy, Suspense } from 'react';
import { Routes, Route } from 'react-router-dom';

// Each of these becomes a separate file: Dashboard-[hash].js, etc.
// Dashboard.js is NOT in the initial bundle — it loads on demand.
const Dashboard = lazy(() => import('./pages/Dashboard'));
const Settings  = lazy(() => import('./pages/Settings'));
const Reports   = lazy(() => import('./pages/Reports'));

function App() {
  return (
    // Suspense shows a fallback while the chunk loads over the network
    <Suspense fallback=<PageSkeleton />>
      <Routes>
        <Route path="/dashboard" element=<Dashboard /> />
        <Route path="/settings"  element=<Settings />  />
        <Route path="/reports"   element=<Reports />   />
      </Routes>
    </Suspense>
  );
}

Web Security — What It Is and Why It Matters

Security in a UI app operates at multiple layers: what the browser enforces (CSP), what the network enforces (HTTPS, CORS), and what your pipeline enforces (secrets management, image scanning). Each layer is independent — a failure in one does not protect the others.

Content Security Policy (CSP) — Deep Explanation

CSP is an HTTP response header that tells the browser what content it is allowed to load and execute. Without it, if an attacker injects a <script> tag (XSS), the browser happily executes it. With a strict CSP, the browser refuses to execute any script not explicitly whitelisted.

The most important directive is script-src. Using 'nonce-{random}' means only scripts carrying a server-generated nonce attribute can execute — an attacker injecting a script tag cannot know the nonce. 

HTTP Response HeaderContent-Security-Policy:
  default-src 'self';

  # Only scripts with matching nonce="" attribute may execute.
  # The nonce is generated per-request — never reuse.
  script-src  'self' 'nonce-{SERVER_NONCE_PER_REQUEST}';

  # Same for inline styles
  style-src   'self' 'nonce-{SERVER_NONCE_PER_REQUEST}';

  # Allow images from self and your CDN
  img-src     'self' data: https://cdn.example.com;

  # Allow fonts from self and Google Fonts
  font-src    'self' https://fonts.gstatic.com;

  # Allow API calls only to known domains
  connect-src 'self' https://api.example.com wss://realtime.example.com;

  # Prevent this page from being loaded in an iframe (clickjacking)
  frame-ancestors 'none';

  # Report violations to your monitoring endpoint
  report-to   default;
Express + Helmet — generate nonce per requestimport helmet   from 'helmet';
import crypto   from 'crypto';

// Middleware: attach a fresh nonce to every response
app.use((req, res, next) => {
  res.locals.nonce = crypto.randomBytes(16).toString('base64');
  next();
});

app.use((req, res, next) => helmet({
  contentSecurityPolicy: {
    directives: {
      defaultSrc:     ["'self'"],
      scriptSrc:      ["'self'", () => `'nonce-${res.locals.nonce}'`],
      styleSrc:       ["'self'", () => `'nonce-${res.locals.nonce}'`],
      frameAncestors: ["'none'"],
      connectSrc:     ["'self'", 'https://api.example.com'],
    },
  },
  hsts: { maxAge: 63072000, includeSubDomains: true, preload: true },
})(req, res, next));

// In your SSR template, apply the nonce to every inline script/style:
// <script nonce="<%= nonce %>">...</script>

CORS — What It Protects and How

CORS (Cross-Origin Resource Sharing) is a browser mechanism that prevents malicious websites from making API calls on behalf of an authenticated user. When app.evil.com tries to fetch('https://api.yourapp.com/user'), the browser sends a preflight OPTIONS request first. The server must respond with an Access-Control-Allow-Origin header matching the requesting origin — otherwise the browser blocks the response.

⚠️

CORS protects users, not servers. CORS is enforced by browsers only. A server-to-server request (curl, Postman, your backend service) ignores CORS entirely. Use CORS to prevent unauthorized browser-based calls, but always validate authorization server-side. 

Express — strict CORS configurationimport cors from 'cors';

// Allowed origins come from environment config — not hardcoded
const allowedOrigins = process.env.ALLOWED_ORIGINS.split(',');
// e.g. "https://app.example.com,https://staging.example.com"

app.use(cors({
  origin(origin, callback) {
    // Allow server-to-server calls (no Origin header) or whitelisted origins
    if (!origin || allowedOrigins.includes(origin)) {
      callback(null, true);
    } else {
      callback(new Error(`CORS: origin ${origin} not permitted`));
    }
  },
  credentials: true,   // allow cookies / Authorization header
  maxAge: 86400,         // cache preflight for 24h — reduces OPTIONS requests
}));

Secrets Management — Why Frontend Env Vars Are NOT Secrets

When you run npm run build, Vite replaces every import.meta.env.VITE_* reference in your source code with the literal string value. This means the value ends up verbatim in your JavaScript bundle on the CDN — accessible to anyone who opens DevTools. 

CORRECT vs WRONG secret handling// ✅ SAFE: public config — CDN URL, feature flags, env name
const apiUrl = import.meta.env.VITE_API_URL;   // "https://api.example.com"

// ❌ NEVER: these WILL appear in your bundle for anyone to read
const key    = import.meta.env.VITE_STRIPE_SECRET_KEY;
const dbPass = import.meta.env.VITE_DB_PASSWORD;

// ✅ Secrets belong in your backend, fetched via authenticated API:
// Frontend calls  GET /api/payment-intent  (authenticated request)
// Backend uses    process.env.STRIPE_SECRET_KEY  (never exposed to browser)
OWASP Risk Attack Scenario Defense
A03 — XSS Attacker injects <script> via user content React auto-escapes JSX. For raw HTML: DOMPurify. Add nonce-based CSP.
A02 — Crypto Failure JWT stored in localStorage — stolen by XSS Store auth tokens in httpOnly; Secure; SameSite=Strict cookies. JS cannot read httpOnly cookies.
A05 — Broken Access Control Hide admin route in React but skip server auth check Client-side route guards are UX only. Every API endpoint must validate authorization independently.
A08 — Software Integrity Third-party CDN script is compromised Add integrity="sha256-..." SRI hash to all external scripts. Browser refuses to execute if hash doesn't match.

Docker — What It Is and How It Works

A container is not a virtual machine. A VM emulates an entire computer including the kernel. A container shares the host OS kernel but isolates the filesystem, processes, and network. Containers start in milliseconds, use MBs of RAM, and are perfectly reproducible.

Images vs Containers

Docker Image

A read-only template. Like a class in OOP. Contains the filesystem snapshot: OS libs, your code, nginx binary. Stored in ECR.

Built with docker build. Tagged with a version (:abc12345).

Docker Container

A running instance of an image. Like an object instance. Has its own writable layer, process space, and network interface.

Created with docker run. In K8s, containers run inside Pods.

How Docker Layers Work

A Dockerfile creates a layer for each instruction. Layers are cached. When you rebuild, Docker only re-runs instructions where the layer's input changed. This is why you copy package.json and run npm ci before copying the rest of your source — the deps layer stays cached unless you change package.json. 

Dockerfile — layer caching strategy explained# Layer 1: base image — rarely changes, always cached
FROM node:20-alpine AS deps

WORKDIR /app

# Layer 2: ONLY package files — cached unless deps change
# If you changed src/Button.tsx but not package.json,
# this layer (and npm ci) is served from cache — FAST.
COPY package.json package-lock.json ./
RUN npm ci --prefer-offline

# Layer 3: source code — changes on every commit
# This layer is never cached. That's fine — it's just a file copy.
COPY . .

# Layer 4: run build — only executes if layer 3 changed
RUN npm run build

# ── New stage: production image ──────────────────────────────
# IMPORTANT: multi-stage means the node_modules and source code
# from the builder stage are NEVER included in the final image.
# Only dist/ is copied. Final image: ~25 MB instead of 1.1 GB.
FROM nginx:1.27-alpine AS production

RUN rm /etc/nginx/conf.d/default.conf
COPY nginx/nginx.conf /etc/nginx/conf.d/app.conf
COPY --from=deps /app/dist /usr/share/nginx/html

# Security: run as non-root user (uid 101 = nginx user in alpine image)
USER nginx
EXPOSE 8080
CMD ["nginx", "-g", "daemon off;"]
⟶ How this image gets to ECR

CodeBuild runs docker build on this Dockerfile. It then calls aws ecr get-login-password (which uses the CodeBuild IAM role — no stored credentials) to get a temporary token. docker login uses that token. Then docker push uploads the image layers to ECR.

The image is tagged with the git SHA (:abc12345) so you can always trace which commit produced which running pod.

nginx.conf for a React SPA

The try_files $uri $uri/ /index.html directive is critical for SPAs. When a user deep-links to /dashboard/settings, nginx looks for a file called dashboard/settings (doesn't exist), then falls back to index.html. React Router then reads the URL and renders the correct component. 

nginx/nginx.confserver {
    listen      8080;
    server_name _;
    root        /usr/share/nginx/html;
    index       index.html;

    # Gzip: compress JS/CSS before sending — saves ~60-70% bandwidth
    gzip            on;
    gzip_types      text/plain text/css application/javascript
                    application/json application/xml image/svg+xml;
    gzip_min_length 256;
    gzip_vary       on;   # adds Vary: Accept-Encoding header for CDN correctness

    # Hashed static assets: cache forever, browser won't recheck
    location ~* \.(js|css|woff2|avif|webp|png|jpg|svg)$ {
        add_header Cache-Control "max-age=31536000, immutable";
        try_files $uri =404;
    }

    # SPA root: no-cache + fallback to index.html for client-side routing
    location / {
        add_header Cache-Control "no-cache, no-store, must-revalidate";
        try_files $uri $uri/ /index.html;
    }

    # Healthcheck endpoint — K8s probes hit this to verify the pod is alive
    location /healthz {
        access_log off;
        return 200 "OK";
        add_header Content-Type text/plain;
    }

    add_header X-Content-Type-Options "nosniff"  always;
    add_header X-Frame-Options         "DENY"     always;
}

Docker Compose — Local Full-Stack Development

Docker Compose is a tool to define and run multi-container applications with a single command. Instead of manually starting a frontend server, an API server, and a database in three terminals, one docker compose up starts everything with the correct networking and dependencies.

How Containers Talk to Each Other

Compose creates a private network for all services in the same file. Services find each other using their service name as hostname. When the ui container makes a request to http://api:3001, Docker resolves api to the internal IP of the api container. No IP addresses needed. 

docker-compose.yml — annotatedversion: '3.9'

services:

  ui:
    build:
      context: .
      # Use "deps" stage (has node_modules) for dev, not the nginx prod stage
      target: deps
    command: npm run dev -- --host 0.0.0.0
    volumes:
      # Mount src/ from host into container — changes appear instantly (HMR)
      - ./src:/app/src
      # Anonymous volume: keeps the container's node_modules separate from host.
      # Without this, the host node_modules folder would overwrite the container's.
      - /app/node_modules
    ports:
      - "5173:5173"   # host:container — access at localhost:5173
    environment:
      # "api" here is the Compose service name — Docker DNS resolves it
      - VITE_API_URL=http://api:3001
    depends_on:
      api:
        condition: service_healthy   # wait until API passes health check

  api:
    build: ./api
    command: node --watch server.js   # Node 20+ built-in watch mode
    volumes:
      - ./api:/app
      - /app/node_modules
    ports:
      - "3001:3001"
    environment:
      # Service name "db" resolves to Postgres container inside Docker network
      - DATABASE_URL=postgres://appuser:devpass@db:5432/appdb
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:3001/health"]
      interval: 10s
      timeout:  5s
      retries:  3
    depends_on:
      db:
        condition: service_healthy

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB:       appdb
      POSTGRES_USER:     appuser
      POSTGRES_PASSWORD: devpass
    volumes:
      # Named volume persists DB data across container restarts
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U appuser"]
      interval: 5s
      retries:  5

volumes:
  pgdata:    # named volume — survives "docker compose down", deleted by "down -v"
Shell — common Compose commands# Start everything (build if needed), stream logs
docker compose up --build

# Run in background, then tail logs for one service
docker compose up -d
docker compose logs -f ui

# Run a one-off command in the ui container (e.g., run tests)
docker compose run --rm ui npm test

# Stop and remove containers (keep volumes)
docker compose down

# Stop and remove containers AND volumes (wipes DB data)
docker compose down -v

IAM — The Authentication Glue

IAM (Identity and Access Management) is the system that grants AWS services permission to call other AWS services. Understanding IAM is understanding how the pipeline works. Every broken pipeline comes down to a missing IAM permission.

How IAM Roles Work (No Keys Required)

When CodeBuild runs your buildspec.yml, it assumes an IAM service role. AWS automatically injects temporary credentials (access key + secret + session token) into the build environment via the EC2 Instance Metadata Service. The AWS CLI and SDK automatically find and use these — you never handle keys manually.

IRSA — IAM Roles for K8s Service Accounts

Inside EKS pods, you cannot use the node's IAM role for fine-grained access — all pods on the node would share the same permissions. IRSA (IAM Roles for Service Accounts) links a Kubernetes ServiceAccount to an IAM role using OpenID Connect (OIDC). The pod gets a projected JWT token that it exchanges with AWS STS for temporary IAM credentials. 

Setting up IRSA — step by step# 1. Enable OIDC provider on EKS cluster (once per cluster)
eksctl utils associate-iam-oidc-provider \
  --cluster my-cluster --region us-east-1 --approve

# 2. Create IAM role with trust policy that allows the K8s service account
eksctl create iamserviceaccount \
  --cluster   my-cluster \
  --namespace production \
  --name      ui-app-sa \
  --attach-policy-arn arn:aws:iam::aws:policy/SecretsManagerReadWrite \
  --approve

# 3. Annotate the K8s ServiceAccount (eksctl does this automatically)
kubectl annotate serviceaccount ui-app-sa \
  -n production \
  eks.amazonaws.com/role-arn=arn:aws:iam::123456789:role/ui-app-irsa-role
k8s/serviceaccount.yamlapiVersion: v1
kind:       ServiceAccount
metadata:
  name:      ui-app-sa
  namespace: production
  annotations:
    # This annotation is what links K8s SA to IAM role via OIDC
    eks.amazonaws.com/role-arn: arn:aws:iam::123456789:role/ui-app-irsa-role

ECR — Elastic Container Registry

ECR is AWS's managed Docker image registry. It replaces Docker Hub for private images and integrates natively with IAM — no separate registry credentials to manage.

How CodeBuild Authenticates to ECR

ECR uses temporary authentication tokens (valid 12 hours). You request one using your IAM credentials, then feed it to docker login. The token is never stored permanently. 

buildspec.yml — ECR login (no password ever hardcoded)# This command uses the CodeBuild IAM role (auto-injected as env creds)
# to call the ECR API and get a 12-hour base64-encoded password.
# That password is piped directly into docker login — never stored.
aws ecr get-login-password --region us-east-1 | \
  docker login \
    --username AWS \
    --password-stdin \
    123456789.dkr.ecr.us-east-1.amazonaws.com

# After login, docker push/pull works normally to this registry

Image Tagging Strategy

buildspec.yml — tagging# Short git SHA — ties every image to exact source commit
IMAGE_TAG=$(echo $CODEBUILD_RESOLVED_SOURCE_VERSION | cut -c1-8)

# Full ECR URI with tag
IMAGE_URI=123456789.dkr.ecr.us-east-1.amazonaws.com/my-ui-app:$IMAGE_TAG

# Build with two tags: specific SHA + :latest for layer cache reference
docker build \
  --cache-from 123456789.dkr.ecr.us-east-1.amazonaws.com/my-ui-app:latest \
  -t $IMAGE_URI \
  -t 123456789.dkr.ecr.us-east-1.amazonaws.com/my-ui-app:latest \
  .

docker push $IMAGE_URI
docker push 123456789.dkr.ecr.us-east-1.amazonaws.com/my-ui-app:latest

# Write the tag to a file — passed as artifact to the deploy stage
echo $IMAGE_TAG > image-tag.txt

How EKS Nodes Pull from ECR

EKS worker nodes run on EC2 instances with a node IAM role. That role must have ecr:GetAuthorizationToken and ecr:BatchGetImage permissions. The kubelet (K8s agent on each node) uses this role to authenticate to ECR and pull images when creating pods. You do not configure this per-pod — it works at the node level automatically.

AWS CodeBuild — Deep Dive

CodeBuild is a fully managed CI server. When triggered, AWS launches a fresh build container (the compute environment), downloads your source from S3 (the CodePipeline artifact), and executes your buildspec.yml phases sequentially. The container is destroyed after the build — every build starts clean.

buildspec.yml — Phase Anatomy

Each phase runs shell commands sequentially. If any command returns a non-zero exit code, the phase fails and the pipeline stops. 

buildspec.yml — complete annotatedversion: 0.2

# ── Environment variables ─────────────────────────────────────
# CodeBuild injects these before any phase runs.
# parameter-store: fetches from AWS SSM Parameter Store (safe, audited)
# secrets-manager: fetches from AWS Secrets Manager (auto-rotated)
env:
  variables:
    NODE_ENV: production
    ECR_REGISTRY: 123456789.dkr.ecr.us-east-1.amazonaws.com
    ECR_REPO:     my-ui-app
  parameter-store:
    VITE_API_URL: /myapp/prod/api-url   # safe non-secret config
  secrets-manager:
    SONAR_TOKEN:  myapp/sonar-token    # secret — never in env files

phases:

  install:
    # Declares which runtime version to use.
    # CodeBuild's managed image includes Node LTS versions.
    runtime-versions:
      nodejs: 20
    commands:
      - echo "=== INSTALL ==="
      # npm ci is stricter than npm install:
      # - uses exact versions from package-lock.json
      # - fails if lock file is out of sync
      # - deletes node_modules first for clean install
      - npm ci --prefer-offline

  pre_build:
    commands:
      - echo "=== PRE-BUILD: quality gates ==="
      - npm run lint           # ESLint — code quality
      - npm run type-check     # tsc --noEmit — type safety
      - npm run test -- --coverage --ci
        --coverageThreshold='{"global":{"lines":80}}'

      # ECR login — uses IAM role, no password stored anywhere
      - aws ecr get-login-password --region us-east-1 |
          docker login --username AWS --password-stdin $ECR_REGISTRY

      # Derive image tag from git commit SHA (first 8 chars)
      - export IMAGE_TAG=$(echo $CODEBUILD_RESOLVED_SOURCE_VERSION | cut -c1-8)
      - export IMAGE_URI=$ECR_REGISTRY/$ECR_REPO:$IMAGE_TAG

  build:
    commands:
      - echo "=== BUILD: docker image ==="
      # --cache-from pulls the :latest image from ECR before building.
      # Docker reuses any unchanged layers from :latest — speeds up builds.
      # The VITE_API_URL build-arg is public config — safe to bake into bundle.
      - docker build
          --build-arg VITE_API_URL=$VITE_API_URL
          --cache-from $ECR_REGISTRY/$ECR_REPO:latest
          -t $IMAGE_URI
          -t $ECR_REGISTRY/$ECR_REPO:latest
          .

  post_build:
    commands:
      - echo "=== POST-BUILD: scan + push ==="

      # Trigger ECR image scan for OS CVEs before pushing
      - aws ecr start-image-scan
          --repository-name $ECR_REPO
          --image-id imageTag=$IMAGE_TAG
      - aws ecr wait image-scan-complete
          --repository-name $ECR_REPO
          --image-id imageTag=$IMAGE_TAG

      # Push both specific SHA tag and :latest
      - docker push $IMAGE_URI
      - docker push $ECR_REGISTRY/$ECR_REPO:latest

      # Write image tag to file — the deploy stage reads this to know which tag to deploy
      - echo $IMAGE_TAG > image-tag.txt
      - printf '{"imageUri":"%s"}' $IMAGE_URI > imagedefinitions.json

# Artifacts are zipped and stored in the CodePipeline S3 bucket.
# The deploy stage downloads this zip and reads image-tag.txt.
artifacts:
  files:
    - image-tag.txt
    - imagedefinitions.json
    - helm/**           # include helm chart for deploy stage

# Cache node_modules in S3 — restored at the start of next build.
# Reduces install time from ~60s to ~5s on cache hit.
cache:
  paths:
    - node_modules/**/*
    - /root/.npm/**/*

AWS CodePipeline — How It Orchestrates Everything

CodePipeline is the conductor. It does not build or deploy anything itself — it watches a source, sequences stages, passes artifacts between stages (via S3), and triggers CodeBuild projects or Lambda functions at each stage.

CloudFront + S3 — CDN Delivery

CloudFront is a CDN (Content Delivery Network) with 400+ edge locations worldwide. When a user in Tokyo requests your app, CloudFront serves it from its Tokyo edge — not your us-east-1 origin. This reduces latency dramatically.

How CloudFront Caching Works

CloudFront checks its edge cache first. On cache miss, it forwards the request to the origin (S3 bucket or ALB). The origin's Cache-Control response header tells CloudFront how long to cache the response at the edge. The next user in the same region gets the cached copy instantly.

CodeBuild Deploy Step — S3 + CloudFront Invalidation

buildspec-deploy-s3.ymlpost_build:
  commands:
    # Upload hashed assets first — they can have long cache headers
    # Exclude index.html from this sync (handled separately below)
    - aws s3 sync dist/ s3://$BUCKET_NAME/
        --cache-control "max-age=31536000,immutable"
        --exclude "index.html"
        --delete          # remove assets that no longer exist in dist/

    # Upload index.html with strict no-cache
    # This is the last step — ensures users get the new hashes only
    # after all new assets are already uploaded
    - aws s3 cp dist/index.html s3://$BUCKET_NAME/index.html
        --cache-control "no-cache,no-store,must-revalidate"
        --content-type "text/html; charset=utf-8"

    # Invalidate only index.html — NOT /* (wildcard costs per path)
    # Assets are cache-busted by new hashes — no invalidation needed
    - aws cloudfront create-invalidation
        --distribution-id $CF_DISTRIBUTION_ID
        --paths "/index.html"

Kubernetes — Concepts from the Ground Up

Kubernetes is a container orchestration platform. You tell it "I want 3 copies of this Docker image running, each with these environment variables and resource limits." K8s handles scheduling them onto nodes, restarting crashed containers, and scaling them up when CPU is high.

Core Objects You Must Know

🫛
Pod
The smallest deployable unit. Contains one or more containers that share network and storage. You rarely create pods directly — Deployments manage them.
📋
Deployment
Manages a set of identical pods. Declares desired state (replicas, image, strategy). K8s continuously reconciles actual state to match desired state.
🔌
Service
A stable network endpoint for a set of pods. Pods come and go (restarts, scaling) but the Service IP stays constant. Other services talk to it via the Service name.
🚪
Ingress
HTTP routing rules. "Route all traffic to app.example.com → Service my-ui-app-svc." On EKS, the AWS Load Balancer Controller reads Ingress objects and creates an ALB.
🗺️
ConfigMap
Key-value store for non-secret config. Mounted into pods as environment variables or files. Change a ConfigMap and redeploy to update config without rebuilding the image.
🔐
Secret
Like ConfigMap but for sensitive data (base64-encoded, not encrypted by default). For real security, use Secrets Store CSI Driver + AWS Secrets Manager.
📊
HPA
Horizontal Pod Autoscaler. Watches CPU/memory metrics and automatically scales replicas up (traffic spike) or down (quiet hours). Works with the Deployment.
🛡️
PodDisruptionBudget
Guarantees minimum availability during voluntary disruptions (rolling updates, node drains). Prevents K8s from killing all pods simultaneously.

How Rolling Updates Work (Zero Downtime)

When you update a Deployment (new image tag), K8s performs a rolling update: it creates a new pod, waits for its readiness probe to pass, then terminates an old pod. It repeats until all pods run the new version. With maxUnavailable: 0, old pods are never terminated before new ones are ready. 

k8s/deployment.yaml — annotatedapiVersion: apps/v1
kind:       Deployment
metadata:
  name:      my-ui-app
  namespace: production
spec:
  replicas: 3   # K8s always maintains exactly 3 pods

  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge:       1   # create 1 extra pod before killing any → briefly 4 pods
      maxUnavailable: 0   # never have fewer than 3 ready pods

  selector:
    matchLabels:
      app: my-ui-app   # Service uses this same label to find pods

  template:
    metadata:
      labels:
        app: my-ui-app
    spec:

      serviceAccountName: ui-app-sa   # links to IRSA role for Secrets Manager access

      containers:
        - name:  ui
          image: 123456789.dkr.ecr.us-east-1.amazonaws.com/my-ui-app:abc12345

          ports:
            - containerPort: 8080   # must match nginx EXPOSE port

          resources:
            requests:              # scheduler uses these to find a node with enough capacity
              cpu:    "100m"        # 100 millicores = 0.1 vCPU
              memory: "128Mi"
            limits:                # container is throttled/killed if it exceeds these
              cpu:    "500m"
              memory: "256Mi"

          # livenessProbe: if this fails 3 times, K8s RESTARTS the container
          livenessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 10   # wait for nginx to start
            periodSeconds:       10

          # readinessProbe: if this fails, pod is REMOVED from Service (no traffic sent)
          # This is what makes rolling updates safe — new pod only gets traffic when ready
          readinessProbe:
            httpGet:
              path: /healthz
              port: 8080
            initialDelaySeconds: 3
            periodSeconds:       5

          securityContext:
            runAsNonRoot:             true    # reject if image user is root
            runAsUser:                101     # nginx user in alpine
            readOnlyRootFilesystem:   true    # container cannot write to its own filesystem
            allowPrivilegeEscalation: false   # cannot gain more privileges than parent process

AWS EKS — Managed Kubernetes

EKS runs the Kubernetes control plane (API server, scheduler, etcd) for you across multiple AZs. You only manage worker nodes (EC2 instances or Fargate) where your pods actually run. The big advantage: no patching the control plane, automatic version upgrades.

How CodeBuild Authenticates to EKS

EKS uses AWS IAM for authentication. When CodeBuild runs aws eks update-kubeconfig, it calls the EKS API using its IAM role, which returns a kubeconfig file. This kubeconfig contains a command (aws eks get-token) that generates a temporary bearer token for kubectl/helm to use.

But EKS also has a Kubernetes-level authorization layer. The IAM role must be listed in the aws-auth ConfigMap for the K8s API to grant it access.

Ingress + AWS Load Balancer Controller

A K8s Service of type ClusterIP is only reachable inside the cluster. To expose it to the internet, you need an Ingress object. On EKS, the AWS Load Balancer Controller (a K8s operator — a program running as a pod) watches for Ingress objects and automatically creates and configures an ALB to match. 

k8s/service.yaml + ingress.yaml — annotated---  Service: stable internal endpoint for the pods ---
apiVersion: v1
kind: Service
metadata:
  name:      my-ui-app-svc
  namespace: production
spec:
  type: ClusterIP   # internal only. ALB connects to pods directly (target-type: ip)
  selector:
    app: my-ui-app   # selects pods with this label — same label as Deployment
  ports:
    - port: 80           # service listens on 80
      targetPort: 8080  # forwards to container port 8080 (nginx)

---  Ingress: AWS LBC reads this and creates an ALB ---
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name:      my-ui-app-ingress
  namespace: production
  annotations:
    # Tell LBC to create an internet-facing ALB (vs. internal)
    kubernetes.io/ingress.class:             alb
    alb.ingress.kubernetes.io/scheme:        internet-facing
    # Connect directly to pod IPs — better performance than node ports
    alb.ingress.kubernetes.io/target-type:   ip
    # ACM certificate ARN for TLS — LBC provisions HTTPS listener automatically
    alb.ingress.kubernetes.io/certificate-arn: arn:aws:acm:us-east-1:123:cert/abc
    # Use TLS 1.3 only policy
    alb.ingress.kubernetes.io/ssl-policy:    ELBSecurityPolicy-TLS13-1-2-2021-06
    # Create both HTTP (redirect) and HTTPS listeners
    alb.ingress.kubernetes.io/listen-ports:  '[{"HTTPS":443},{"HTTP":80}]'
    # Redirect HTTP → HTTPS
    alb.ingress.kubernetes.io/actions.ssl-redirect: >
      {"Type":"redirect","RedirectConfig":{"Protocol":"HTTPS","StatusCode":"HTTP_301"}}
spec:
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: my-ui-app-svc
                port:
                  number: 80
⟶ The full connection: User → CloudFront → ALB → K8s pods

1. User requests https://app.example.com/dashboard

2. DNS points to CloudFront distribution. CloudFront checks cache — miss → forwards to ALB origin.

3. ALB receives request. Checks rules → routes to target group (pods with label app=my-ui-app).

4. ALB picks a pod IP (registered by AWS LBC), sends HTTP to port 8080.

5. nginx receives the request. try_files falls back to index.html. Response flows back.

6. CloudFront caches the response (if Cache-Control allows). Returns to user.

Helm — What It Is and Why You Need It

Without Helm, you maintain separate YAML files for staging and production. When you add a feature (new env var, new resource limit), you must update both files. With Helm, you have one set of templates with placeholder variables ({{ .Values.image.tag }}), and separate values files per environment.

Helm Architecture

Without Helm

  • staging/deployment.yaml
  • staging/service.yaml
  • staging/ingress.yaml
  • prod/deployment.yaml (duplicate)
  • prod/service.yaml (duplicate)
  • Every change must be made in all copies

With Helm

  • templates/deployment.yaml (one template)
  • templates/service.yaml
  • templates/ingress.yaml
  • values.yaml (defaults)
  • values-staging.yaml (overrides)
  • values-prod.yaml (overrides)

Helm Deploy, Upgrade & Rollback

The helm upgrade --install Command Explained

helm upgrade --install is the idempotent deploy command. If the release does not exist, it installs it. If it does, it upgrades it. You always use this in CI — never separate install and upgrade commands. 

buildspec-deploy.yml — Helm deploy stepbuild:
  commands:
    # Update kubeconfig to point kubectl/helm at the right EKS cluster
    # Uses CodeBuild IAM role (auto-injected) — no stored credentials
    - aws eks update-kubeconfig
        --name   $CLUSTER_NAME
        --region us-east-1

    # Read the image tag that the Build stage wrote to image-tag.txt
    # CodePipeline passed it as an artifact to this stage
    - IMAGE_TAG=$(cat image-tag.txt)

    # Lint the chart first — catches YAML errors before touching the cluster
    - helm lint helm/my-ui-app

    # Dry-run: render templates + validate against K8s API (--dry-run=server)
    # Does NOT apply anything. Useful for debugging template rendering.
    - helm upgrade --dry-run --install my-ui-app helm/my-ui-app
        --namespace   $NAMESPACE
        --create-namespace
        -f helm/my-ui-app/values.yaml
        -f helm/my-ui-app/values-$ENVIRONMENT.yaml
        --set image.tag=$IMAGE_TAG

    # Actual deploy:
    # --atomic:   if any pod fails to start, auto-rollback to previous release
    # --timeout:  maximum wait time for pods to become ready
    # --wait:     block until all pods pass readiness probe before returning
    - helm upgrade --install my-ui-app helm/my-ui-app
        --namespace   $NAMESPACE
        --create-namespace
        -f helm/my-ui-app/values.yaml
        -f helm/my-ui-app/values-$ENVIRONMENT.yaml
        --set image.tag=$IMAGE_TAG
        --atomic
        --timeout 5m
        --wait

The artifacts block in buildspec.yml lists files to zip. CodeBuild uploads this zip to S3 as BuildArtifact. The Deploy stage CodeBuild project receives this zip as its input and can read image-tag.txt from it.
5

CodeBuild: Deploy to Staging (helm upgrade)

The deploy CodeBuild project receives the BuildArtifact, reads image-tag.txt, authenticates to the staging EKS cluster, and runs helm upgrade --install. 

buildspec-deploy.yml — deploy to staging# Authenticate to staging EKS cluster
# This writes ~/.kube/config using the CodeBuild IAM role.
# The CodeBuild role ARN must be in the cluster's aws-auth ConfigMap.
aws eks update-kubeconfig \
  --name   my-cluster-staging \
  --region us-east-1

# Read the image tag from the artifact file
IMAGE_TAG=$(cat image-tag.txt)

# Deploy with Helm
# -f: merge values in order: defaults ← staging overrides
# --set: highest priority — overrides anything in values files
helm upgrade --install my-ui-app helm/my-ui-app \
  --namespace   staging \
  --create-namespace \
  -f helm/my-ui-app/values.yaml \
  -f helm/my-ui-app/values-staging.yaml \
  --set image.tag=$IMAGE_TAG \
  --atomic \     # rolls back automatically if pods don't become ready
  --timeout 5m \
  --wait         # blocks until all pods pass readiness probe
How K8s pulls the image from ECR
When Helm creates the Deployment and pods start, the kubelet on each node calls aws ecr get-authorization-token using the node's IAM instance role (not the pod's). This role must have ecr:GetAuthorizationToken and ecr:BatchGetImage. kubelet caches the token and pulls layers from ECR via HTTPS.
6

CodeBuild: Run E2E Tests on Staging

A separate CodeBuild project (or a post-deploy step) runs Playwright against the staging URL. If tests fail, the pipeline stops here — the broken build never reaches production. 

buildspec-e2e.ymlphases:
  install:

CodePipeline: Manual Approval

The pipeline pauses. An SNS notification is sent to the engineering team (email/Slack). A senior engineer reviews staging, then approves via the AWS Console or CLI.

8

CodeBuild: Deploy to Production (same flow, different cluster)

Exactly the same Helm command as staging, but targeting the production EKS cluster with the production values file. Same image tag that passed staging — no rebuild. 

buildspec-deploy.yml — prod deploy# Same script, different env variables set by CodePipeline
aws eks update-kubeconfig --name my-cluster-prod --region us-east-1

IMAGE_TAG=$(cat image-tag.txt)   # same SHA that was tested on staging

helm upgrade --install my-ui-app helm/my-ui-app \
  --namespace   production \
  --create-namespace \
  -f helm/my-ui-app/values.yaml \
  -f helm/my-ui-app/values-prod.yaml \
  --set image.tag=$IMAGE_TAG \
  --atomic --timeout 5m --wait
What happens inside K8s during the upgrade
Helm renders the templates with the new image.tag. K8s API server accepts the updated Deployment spec. The ReplicaSet controller starts creating new pods. Each new pod: kubelet pulls the new image from ECR, starts nginx, passes readiness probe. Once ready, kube-proxy updates iptables rules to route traffic to the new pod. Old pod is then gracefully terminated (SIGTERM → 30s grace → SIGKILL). Repeats until all pods are updated.
9

CloudFront Invalidation (S3 deploys only)

For container-based deploys (K8s), CloudFront forwards to ALB which already serves the new pods — no invalidation needed. For S3+CloudFront deploys, invalidate only /index.html after uploading new assets. 

Shell# Upload hashed assets (forever cache) first
aws s3 sync dist/ s3://$BUCKET/ \
  --cache-control "max-age=31536000,immutable" \
  --exclude "index.html" --delete

# Upload index.html last (no-cache)
aws s3 cp dist/index.html s3://$BUCKET/index.html \
  --cache-control "no-cache,no-store"

# Only index.html needs invalidation — assets have new names (new hash)
aws cloudfront create-invalidation \
  --distribution-id $CF_DIST_ID \
  --paths "/index.html"

Feature Flags — Decouple Deploy from Release

Feature flags let you deploy code to production but control who sees it. You ship a feature behind a flag that is off for 100% of users. Then gradually roll it out: 1% → 10% → 50% → 100%. If issues appear, flip the flag off instantly — no rollback needed. 

React — LaunchDarkly feature flagimport { useFlags } from 'launchdarkly-react-client-sdk';

export function CheckoutButton() {
  // Flag value comes from LD server — not baked into bundle
  const { newCheckoutFlow } = useFlags();

  return newCheckoutFlow
    ? <CheckoutV2 />   // new flow — enabled for 5% of users
    : <CheckoutV1 />;  // old flow — 95% of users
}

Monitoring & Observability

Observability means being able to answer "what is happening to my app right now?" without needing to add new instrumentation. You need three signal types: metrics (numbers over time), logs (events), and traces (request paths).

Real User Monitoring — Web Vitals

web-vitals measures Core Web Vitals from real user browsers. You send these to your backend and build dashboards. A spike in LCP after a deploy tells you the new build is slower. 

TypeScript — vitals.tsimport { onCLS, onLCP, onINP, onFCP, onTTFB, type Metric } from 'web-vitals';

function sendMetric({ name, value, id, navigationType }: Metric) {
  fetch('/api/rum', {
    method:  'POST',
    headers: { 'Content-Type': 'application/json' },
    // keepalive: survives page navigation — important for unload events
    keepalive: true,
    body: JSON.stringify({
      name,
      value:          Math.round(value),
      id,
      navigationType,
      url:            location.href,
      release:        import.meta.env.VITE_GIT_SHA,  // know which deploy
    }),
  });
}

onLCP(sendMetric);   // Largest Contentful Paint
onINP(sendMetric);   // Interaction to Next Paint
onCLS(sendMetric);   // Cumulative Layout Shift
onFCP(sendMetric);   // First Contentful Paint
onTTFB(sendMetric);  // Time to First Byte

main.tsx — Sentry initimport * as Sentry from '@sentry/react';

Sentry.init({
