🌐 Browser Lifecycle + React Hooks

Where exactly do useEffect and useLayoutEffect sit in the browser's render pipeline?

1. The Full Browser Pipeline

Phase 1
HTML Parsing Starts
Browser reads HTML top-to-bottom. When it hits <script> (without defer/async), it blocks parsing and executes JS immediately.
Phase 2
Scripts Execute React mounts here
ReactDOM.createRoot().render() runs. React builds the virtual DOM, compares it (diff), then updates the real DOM. This is the render phase — pure, no side effects.
Phase 3
DOM is Built → DOMContentLoaded
Initial HTML + DOM fully parsed. document.readyState === "interactive". Images, CSS, fonts may still be loading.
Phase 4 — Inside React
useLayoutEffect Fires Synchronous
Runs immediately after React commits DOM changes but before the browser paints to screen. Blocks paint. Use for measuring DOM (scroll position, layout).
Phase 5
Browser Paints the Frame User sees it
Browser calculates styles, layout, and paints pixels to the screen. The user sees the update. This is the visual commit.
Phase 6 — Inside React
useEffect Fires Asynchronous
Runs after paint. Non-blocking. Perfect for data fetching, subscriptions, event listeners, DOM mutations that don't affect layout.
Phase 7
Images/Fonts Finish → window.load
All external resources loaded. document.readyState === "complete". window.onload fires.

3. useLayoutEffect — The Sync Hook

Runs immediately after React's Commit, before the browser calculates layout and paints.

function Tooltip({ targetRef }) {
  const tooltipRef = useRef(null);
  const [position, setPosition] = useState({ top: 0, left: 0 });

  useLayoutEffect(() => {
    // DOM is updated but NOT painted yet
    const targetRect = targetRef.current.getBoundingClientRect();
    const tooltipHeight = tooltipRef.current.offsetHeight;

    // Calculate position to avoid overflow
    setPosition({
      top: targetRect.bottom + 8,
      left: targetRect.left,
    });
    // This setState triggers a RE-RENDER before paint!
    // Result: user sees correctly positioned tooltip first time
  }, [targetRef]);

  return <div ref={tooltipRef} style={{ position: 'absolute', ...position }}>Tooltip</div>;
}
Why not useEffect here? If you used useEffect, the browser would paint the tooltip at the wrong position first, then correct it — causing a visual flicker.

4. useEffect — The Async Hook

Runs after paint, scheduled as a deferred task. The user already sees the updated UI.

function UserProfile({ userId }) {
  const [user, setUser] = useState(null);

  useEffect(() => {
    // User already sees the loading state / previous data
    fetch(`/api/users/${userId}`)
      .then(r => r.json())
      .then(setUser);
  }, [userId]);

  if (!user) return <Spinner />;
  return <div>{user.name}</div>;
}
Why useEffect here? Data fetching doesn't need to block paint. The user sees a loading spinner immediately, then data fills in. If this were useLayoutEffect, the UI would freeze until the fetch completes.

5. Concrete Comparison: Measuring a Div

function MeasureExample() {
  const divRef = useRef(null);
  const [width, setWidth] = useState(0);

  // ❌ With useEffect: user sees width=0 briefly, then jump
  useEffect(() => {
    setWidth(divRef.current.offsetWidth);
  }, []);

  // ✅ With useLayoutEffect: correct width before paint
  useLayoutEffect(() => {
    setWidth(divRef.current.offsetWidth);
  }, []);

  return <div ref={divRef}>Width: {width}px</div>;
}

6. Another Real Example: Auto-Focus Input

function Modal({ isOpen }) {
  const inputRef = useRef(null);

  useLayoutEffect(() => {
    if (isOpen) {
      inputRef.current?.focus();
      // Focus happens BEFORE paint
      // User sees modal with cursor already blinking
    }
  }, [isOpen]);

  return isOpen ? <input ref={inputRef} /> : null;
}
If you used useEffect, the modal would paint first, then focus would jump — potentially causing a scroll jump or visible focus ring appearing after render.

7. The Golden Rules

📌 Rule 1: Start with useEffect

99% of side effects don't need to block paint. It's the safe default.

📌 Rule 2: Use useLayoutEffect only for layout measurements

Reading DOM size/position and synchronously re-rendering based on it.

📌 Rule 3: useLayoutEffect can cause performance issues

It blocks the browser's paint cycle. If it does heavy work, the UI freezes. Keep it fast.

📌 Rule 4: useEffect with empty deps []

Runs once after initial mount + paint. Equivalent to componentDidMount.

📌 Rule 5: useEffect cleanup

Runs before the component unmounts or before re-running the effect. Use for cleanup (removeEventListener, abort fetch, clearInterval).

8. Summary Table

Hook Runs when Blocks paint? Use for
useEffect After paint ❌ No API calls, subscriptions, timers, analytics
useLayoutEffect Before paint ✅ Yes DOM measurement, preventing flicker, sync focus/scroll

🔴 useLayoutEffect

  • Runs synchronously after DOM mutation
  • Before browser paint
  • Blocks the visual update
  • Can read and synchronously re-write DOM
Use when: Measuring DOM nodes, preventing visual flicker (tooltip positioning), reading scroll position before paint, animating from measured values.

🔵 useEffect

  • Runs asynchronously after paint
  • After browser paint
  • Non-blocking — user sees UI first
  • Standard for side effects
Use when: API calls, subscriptions, timers, event listeners, document title changes, analytics — anything that doesn't need to happen before the user sees the frame.
The key mental model: useLayoutEffect is for when the user must NEVER see the intermediate state. If the first paint looks wrong and needs immediate correction, reach for useLayoutEffect. Otherwise, stick with useEffect.
